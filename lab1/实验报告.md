## 一、实验目的

本实验的主要目的是：

1. 用**链接脚本**描述内核的内存布局，理解可执行文件的段划分（`.text` / `.rodata` / `.data` / `.bss` / 栈）如何被链接器映射到具体地址；
2. 通过**交叉编译**在 x86 主机上生成 RISC-V 64 位目标代码，并掌握 `ELF → 裸二进制镜像` 的转换流程与二者差异；
3. 理解 **QEMU + OpenSBI** 的接力式启动过程：加电复位 → boot ROM → OpenSBI（M 模式）→ 内核（S 模式，0x80200000）；
4. 完成汇编入口 `kern_entry`（建立内核栈并跳入 C 入口），并借助 **OpenSBI 提供的服务**自底向上搭出 `cprintf`，让内核在屏幕上输出第一行信息；
5. 掌握**用 GDB 远程调试内核**的方法，能够跟踪从加电到内核第一条指令的完整过程。

## 三、实验整体逻辑分析

### 3.1 本章节的逻辑主线

本章围绕"**让一台空无一物的 RISC-V 机器说出第一句话**"这一核心主题展开，解决的问题是：在没有任何操作系统、没有任何运行时库可依赖的前提下，如何从零建立一个能编译、能加载、能运行、能输出的最小可执行内核。

整条链路可以概括为四步接力：

> **编译链接**（`kernel.ld` 把内核安排在 0x80200000，入口定为 `kern_entry`）
> → **加载运行**（QEMU 模拟硬件，OpenSBI 固件完成机器态初始化并把控制权交给内核）
> → **建立 C 运行环境**（`entry.S` 建立内核栈、跳入 C 入口，`kern_init` 清除 `.bss`）
> → **输出反馈**（自底向上封装 `sbi_call → cons_putc → cprintf`，打印出 `(THU.CST) os is loading ...`）。

### 3.2 功能的逐步实现

1. **首先确定内核在内存中的位置与入口** → 用链接脚本 `tools/kernel.ld` 指定 `BASE_ADDRESS = 0x80200000` 与 `ENTRY(kern_entry)`。**为什么先做这一步**：地址是后面一切的前提——内核必须被加载到 OpenSBI 跳转的目标地址上，且入口符号必须存在，否则控制权交接后无处可去；同时 `. = ALIGN(0x1000)`、`PROVIDE(edata/end)` 等安排，为后面清 `.bss` 提供了符号基础。
2. **接着写汇编入口 `kern_entry`** → 用 `la sp, bootstacktop` 建立内核栈，用 `tail kern_init` 跳入 C。**为什么第二步做这个**：编译器生成的 C 代码默认栈已就绪，而机器刚从固件手中接过控制权时 `sp = 0`（实测见练习 2），不先建栈，任何 C 函数调用都会立即失败；这一步是"从汇编世界进入 C 世界"的必经关口。
3. **然后由 `kern_init` 完成最小初始化并给出可视化反馈** → `memset(edata, 0, end - edata)` 清 `.bss`，随后 `cprintf` 打印信息、进入死循环。**为什么第三步做这个**：`.bss` 段在镜像中不保存数据，必须由内核自己清零；而"能打印"是后续所有实验的调试基础设施，没有输出就无法验证任何功能。
4. **最后解决"输出从哪来"的问题** → 自底向上封装：`sbi_call`（内联汇编 + `ecall` 陷入 M 模式）→ `sbi_console_putchar` → `cons_putc` → `cputch`/`cputs` → `printfmt` → `cprintf`。**为什么放在最后**：它是本章唯一"需要层层搭建"的部分——不能使用 glibc 的 `printf`（那要求先有一个操作系统，构成鸡生蛋问题），只能从硬件/固件提供的最原始接口（输出一个字符）开始，一层层包装出格式化输出能力。

此外，整个实验还依赖一套"看不见的支撑"：`Makefile` 负责交叉编译、链接、`objcopy` 生成裸镜像并用 QEMU 启动，使上述四步可以通过 `make` / `make qemu` 一键完成。

### 3.3 核心函数与功能模块的理解

#### 3.3.1 链接脚本 `tools/kernel.ld`：决定内核"住在哪里"

链接脚本是链接器 `ld` 的输入，作用是描述如何把输入目标文件（`.o`）的各段映射到输出文件（ELF）的段，并规定这些段的地址。本实验的脚本里有四个要点：

- `OUTPUT_ARCH(riscv)`：输出文件的目标架构；
- `ENTRY(kern_entry)`：指定 ELF 的入口符号。这个值会写进 ELF 头，`objcopy` 之后的裸镜像也以它为第一条指令所在位置，因此程序里必须真的存在一个名为 `kern_entry` 的符号（由 `entry.S` 提供）；
- `BASE_ADDRESS = 0x80200000`，并用 `. = BASE_ADDRESS;` 把定位计数器 `.` 置于该地址，随后依次排布 `.text`、`.rodata`、`.data`、`.sdata`、`.bss`。选 0x80200000 的原因是 0x80000000 起的一段内存被 OpenSBI 固件占用（实测启动日志中 `Domain0 Region02 : 0x0000000080000000-0x000000008003ffff` 即固件的可执行区域），内核必须落在固件之上；同时这也是 QEMU 为 RISC-V 约定的内核加载地址。段之间用 `. = ALIGN(0x1000);` 对齐到页边界，为后续实验引入分页做准备；
- `PROVIDE(etext = .)`、`PROVIDE(edata = .)`、`PROVIDE(end = .)`：定义三个边界符号。`edata` 指向已初始化数据段的结束、`end` 指向 `.bss` 的结束，`kern_init` 正是用这两个符号来清零 `.bss`。若脚本不提供它们，C 代码里 `extern char edata[], end[]` 的引用会导致链接失败。`/DISCARD/` 则丢弃 `.eh_frame`、`.note.GNU-stack` 等对裸机内核无用的段。

#### 3.3.2 汇编入口 `kern/init/entry.S`：`kern_entry`

这是整个内核的入口，只有三条实质语句，却把机器从"固件刚交棒"的状态带到"可以执行 C"的状态：

- `.section .text,"ax",%progbits` + `.globl kern_entry`：把 `kern_entry` 放进可分配、可执行的 `.text` 段，并使其对外可见，以便链接脚本的 `ENTRY` 能引用到它；
- `la sp, bootstacktop`：建立内核栈（详见练习 1）；
- `tail kern_init`：尾调用跳入 C 入口（详见练习 1）。

同时它在 `.data` 段中用 `.align PGSHIFT`（对齐到 4KB 页）、`.space KSTACKSIZE` 预留内核栈，并用 `bootstack` / `bootstacktop` 标出栈底与栈顶。其作用是**唯一地建立栈**，其他一切（初始化、输出）都交给 C。

#### 3.3.3 C 入口 `kern/init/init.c`：`kern_init`

内核的第一个 C 函数，承担两件事：

1. **清 `.bss`**：`extern char edata[], end[];` 声明链接脚本提供的边界符号，然后 `memset(edata, 0, end - edata)`。`.bss` 段在可执行文件中只记录大小、不保存内容（为节省镜像体积），因此其"初值为 0"的语义必须由运行者保证——在普通程序中这项工作由操作系统的装载器完成，而此处内核就是最底层，只能自己动手。由于编译时使用了 `-nostdinc`（不链接任何运行时库），`memset` 也来自 `libs/string.c` 中自己实现的版本。
2. **输出并停机**：`cprintf("%s\n\n", message)` 打印 `(THU.CST) os is loading ...`，随后 `while (1) ;` 进入死循环。函数声明为 `__attribute__((noreturn))`，与 `entry.S` 中的 `tail` 相呼应。

它是"最小内核"的终点，也是后续所有实验的起点。

#### 3.3.4 SBI 调用层 `libs/sbi.c`：`sbi_call` / `sbi_console_putchar`

这是整个输出链的最底层，解决"内核如何请求固件帮忙"的问题：

- `sbi_call(uint64_t sbi_type, uint64_t arg0, uint64_t arg1, uint64_t arg2)`：用内联汇编实现。先把功能号放进 `x17`（`a7`）、三个参数放进 `x10`–`x12`（`a0`–`a2`），执行 `ecall` 触发从 S 模式到 M 模式的陷阱，固件处理完后把返回值放在 `x10`，再用 `mv %[ret_val], x10` 取回。汇编块用 `volatile` 修饰、并把 `"memory"` 列入 clobber 列表，是为了防止编译器把它优化掉或跨越它做不当的内存重排。
- 为什么必须用内联汇编：C 语言既无法直接执行 `ecall` 这样的特权指令，也无法精确指定"哪个变量进哪个寄存器"，而这正是调用约定所要求的。
- 文件开头定义了 SBI 功能号清单（`SBI_SET_TIMER = 0`、`SBI_CONSOLE_PUTCHAR = 1`、`SBI_CONSOLE_GETCHAR = 2`、`SBI_SHUTDOWN = 8` 等），`sbi_console_putchar(ch)` 就是 `sbi_call(SBI_CONSOLE_PUTCHAR, ch, 0, 0)` 的一行封装；同文件中还预留了 `sbi_set_timer`，供 lab3 的时钟中断使用。

#### 3.3.5 控制台层 `kern/driver/console.c`：`cons_putc`

`void cons_putc(int c) { sbi_console_putchar((unsigned char)c); }` ——只有一行的"薄封装"。它的价值不在实现，而在**接口分层**：上层（`stdio.c`）只依赖"控制台"这一抽象，不直接接触 SBI；日后若要换成真实的 UART 驱动或不同的引导固件，只需改这一层。同文件中的 `cons_init`、`kbd_intr`、`serial_intr` 目前是空实现，`cons_getc` 转调 `sbi_console_getchar`，这些空白正是后续实验的预留接口。

#### 3.3.6 高层 I/O `kern/libs/stdio.c`：`cputch` / `cputchar` / `cputs` / `cprintf` / `vcprintf`

这一层负责"把字符送出去"和"提供好用的打印接口"：

- `static void cputch(int c, int *cnt)`：输出一个字符并把计数加一，是整条输出链的公共出口（**所有**字符最终都经过它）；
- `cputchar(int c)`：单字符输出；
- `cputs(const char *str)`：逐字符输出字符串，末尾自动补一个换行，返回输出的字符数；
- `vcprintf(const char *fmt, va_list ap)`：调用 `vprintfmt((void *)cputch, &cnt, fmt, ap)`，把 `cputch` 作为**回调**交给格式化层，自身只负责计数与返回；
- `cprintf(const char *fmt, ...)`：可变参数版本，用 `va_start/va_end` 取出参数后转交 `vcprintf`。

这种"格式化逻辑与输出目标分离（回调）"的设计使同一套格式化代码可以方便地改写到别的输出目标上。

#### 3.3.7 格式化层 `libs/printfmt.c`：`vprintfmt` / `printnum` / `getint` / `getuint`

`vprintfmt(void (*putch)(int, void *), void *putdat, const char *fmt, va_list ap)` 是"格式化输出"的真正实现：它逐字符扫描格式串，遇到 `%` 就解析标志（`-`、`0`、宽度、长度修饰等）和转换字符（`%d`、`%u`、`%x`、`%o`、`%s`、`%c`、`%p` 等），其中：

- `getint` / `getuint` 根据长度修饰从可变参数列表中取出有符号/无符号整数（对负数的符号扩展必须单独处理，故分成两个函数）；
- `printnum` 以递归方式按任意进制（基数 ≤ 16）逆序输出数字，并支持宽度与前导字符填充；
- 每输出一个字符都回调 `putch`（即 `cputch`），从而最终落到 `cons_putc`。

其与 `cprintf` 的分工可以概括为：`printfmt.c` 管"把格式串和参数变成一串字符"，`stdio.c` 管"把这些字符送出去并计数"。

#### 3.3.8 构建系统 `Makefile` 与 `tools/function.mk`

`Makefile` 定义了工具链与规则（`GCCPREFIX := riscv64-unknown-elf-`、`CC/LD/OBJCOPY`、`CFLAGS := -mcmodel=medany -nostdinc -fno-builtin -ffunction-sections -fdata-sections -g`、`LDFLAGS := -m elf64lriscv -nostdlib --gc-sections`），`function.mk` 提供 `add_files`、`create_target`、`totarget` 等函数式宏，把"遍历目录下的 `.c/.S` 文件并生成编译规则"自动化，最终得到 `bin/kernel`（ELF，供 GDB 使用）与 `bin/ucore.img`（`objcopy --strip-all -O binary` 生成的裸镜像，供 QEMU 装载）。这套结构解释了为什么 lab1 的源文件分放在 `kern/` 与 `libs/` 下、却能一条 `make` 全部编译：目录列表写在 `KSRCDIR` / `LIBDIR` 中，新增文件无需改规则。

## 四、实验内容与实现

### 练习 1：理解内核启动中的程序入口操作

**负责人：** 雷帛霖-2412362

> 题目：阅读 `kern/init/entry.S` 内容代码，结合操作系统内核启动流程，说明指令 `la sp, bootstacktop` 完成了什么操作，目的是什么？`tail kern_init` 完成了什么操作，目的是什么？

#### 解答

**（1）`la sp, bootstacktop` 完成了什么操作，目的是什么？**

`la`（load address）是 RISC-V 汇编中的伪指令，作用是把符号 `bootstacktop` 的**地址**（而不是该地址中存放的内容）装入栈指针寄存器 `sp`。`bootstacktop` 由本文件 `.data` 段中 `.space KSTACKSIZE` 预留的内核栈给出：标号 `bootstack` 位于这块空间的低地址端，`bootstacktop` 位于高地址端。由于 RISC-V 的栈从高地址向低地址增长，"空栈"的栈顶应取高地址端，因此这里装入的是 `bootstacktop`。

这条指令的目的是**为随后运行的 C 代码建立可用的栈**。汇编指令本身不需要栈，但 C 语言的函数调用机制完全建立在栈之上：调用时需要保存返回地址、为局部变量分配空间、保护被调用者需要保持的寄存器，而这一切都通过 `sp` 定位。内核刚接管控制权时 `sp` 处于无效状态（练习 2 中在 0x1000 处实测 `sp = 0`），若不先建立合法栈就跳入 C 函数，第一条需要入栈的指令就会访问非法地址。此外还需注意：这块栈并非运行时"分配"出来的，而是链接时静态划在 `.data` 段中的固定区域，大小由 `memlayout.h` 中的 `KSTACKSIZE`（`KSTACKPAGE × PGSIZE`）决定。

**（2）`tail kern_init` 完成了什么操作，目的是什么？**

`tail` 是尾调用伪指令：它把控制流转移到 `kern_init`，但**不把返回地址写入 `ra`**（实测被汇编为一条无条件跳转 `j 0x8020000a <kern_init>`，而 `call` 会生成 `jal ra, ...`）。其目的是把执行流从汇编入口正式交给 C 入口；同时因为这次跳转不需要返回，采用尾调用形式既符合语义、又省去一个栈帧。

之所以可以（也应该）这样做，是因为 `kern_init` 在 `init.c` 中被声明为 `__attribute__((noreturn))`，并以 `while (1) ;` 结束，永远不会返回到 `kern_entry`。执行完这条指令，汇编的使命（建立栈）全部完成，CPU 开始执行 C 代码。

**实测证据（来自练习 2 的反汇编）：**

```gdb
(gdb) x/10i $pc
=> 0x80200000 <kern_entry>:     auipc   sp,0x3
   0x80200004 <kern_entry+4>:   mv      sp,sp
   0x80200008 <kern_entry+8>:   j   0x8020000a <kern_init>
   0x8020000a <kern_init>:      auipc   a0,0x3
```

`la sp, bootstacktop` 展开为 `auipc` + `addi` 两条（此处的 `addi` 因低 12 位为 0 而显示为 `mv sp,sp`，即把栈顶地址写入 `sp`）；`tail kern_init` 编译为 `j`，与"不写 `ra`"的语义一致。

### 练习 2：使用 GDB 验证启动流程

> 题目：使用 GDB 跟踪 QEMU 模拟的 RISC-V 从加电开始，直到执行内核第一条指令（跳转到 0x80200000）的整个过程。思考并回答：RISC-V 硬件加电后最初执行的几条指令位于什么地址？它们主要完成了哪些功能？

#### 调试方法

QEMU 作为"被调试目标"，GDB 作为"调试器"通过 TCP 端口连接，属于**远程调试**：

- `make debug`：启动 QEMU，`-S` 让虚拟 CPU 一启动就暂停，`-s` 打开 1234 端口等待 GDB 连接；
- `make gdb`：加载 `bin/kernel` 的调试符号（`file bin/kernel`）、设置架构（`set arch riscv:rv64`）、连接目标（`target remote localhost:1234`）。

由于需要同时操作两个程序，使用 tmux 将终端垂直分屏：左侧运行 QEMU，右侧运行 GDB。

#### 问题回答

**（1）RISC-V 硬件加电后最初执行的几条指令位于什么地址？**

位于 **0x1000**。RISC-V 硬件复位时把 PC 强制置为该固定复位地址（QEMU 的 `virt` 机器在此处放置内置的 boot ROM / MROM）。实测连上 GDB 后 `pc = 0x1000`，且该地址处没有符号信息（显示为 `??`），印证它既不属于内核也不属于 OpenSBI。

**（2）它们主要完成了哪些功能？**

从反汇编看，这 6 条指令做的是"**把控制权转交给固件**"这件极其简单的事：

| 指令                | 作用                              |
| ----------------- | ------------------------------- |
| `auipc t0,0x0`    | 取当前 PC 作为基址（0x1000）             |
| `addi a2,t0,40`   | 算出待传递数据的地址（0x1028 附近）           |
| `csrr a0,mhartid` | 读取当前硬件线程（HART）编号，作为第一个参数        |
| `ld a1,32(t0)`    | 从 ROM 数据区取出固件参数（设备树地址）          |
| `ld t0,24(t0)`    | 取出下一步要跳转的目标地址（即 0x80000000）     |
| `jr t0`           | 跳转到 0x80000000 —— OpenSBI 固件的入口 |

即：**读 HART ID、准备参数、取出跳转目标，然后跳到 0x80000000 处的 OpenSBI**。真正的硬件初始化（PMP 配置、时钟、中断委托等）由运行在 M 模式的 OpenSBI 完成，它在初始化结束后按约定跳转到 0x80200000，以内核身份在 S 模式开始执行 `kern_entry`。

**完整启动链（实测印证）：**

```
加电复位（PC ← 0x1000）
  → boot ROM 6 条指令：读 mhartid、准备参数、取跳转目标
  → jr 跳到 0x80000000：OpenSBI（M 模式）初始化并准备下一阶段
  → 跳转 0x80200000（S 模式）：kern_entry
  → la sp, bootstacktop → tail kern_init
  → kern_init：清 .bss → cprintf 输出 → while(1)
  → 串口打印 "(THU.CST) os is loading ..."
```

## 六、实验总结与收获

### 对操作系统的理解

#### 1. 本实验的重要知识点及其与 OS 原理的对应

| 实验中的知识点                                                                           | 对应的 OS 原理                 | 含义、关系与差异                                                                                                                                                                                                                                                                                 |
| --------------------------------------------------------------------------------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 链接脚本与内存布局（`kernel.ld` 中的 `ENTRY(kern_entry)`、`BASE_ADDRESS = 0x80200000`、段的排布与对齐） | 可执行文件的装载与地址空间             | **含义**：链接脚本描述"输入段到输出段"的映射并决定各段的加载地址；OS 原理中的装载指把可执行文件按段放入地址空间的指定位置。**关系**：本实验是一次最原始的静态装载——内核被直接放进 0x80200000。**差异**：真实操作系统中由引导程序或 `exec` 在运行时装载，并借助页表把链接时的虚拟地址映射到物理页；本实验没有 MMU、没有虚拟地址概念，链接地址就是物理地址。                                                                                       |
| `.text` / `.rodata` / `.data` / `.bss` 段的划分与 `.bss` 清零                            | 进程与内核映像的段结构               | **含义**：可执行文件按访问属性分段，`.bss` 只记录大小、不保存内容。**关系**：内核映像与用户程序映像的段划分规则完全一致，`kern_init` 中"清零未初始化数据"正是段语义的体现。**差异**：用户程序的 `.bss` 由操作系统的装载器负责清零，而此处没有更底层的东西可依赖，只能由内核自己用 `memset(edata, 0, end - edata)` 完成，两个边界符号由链接脚本 `PROVIDE` 提供。                                                               |
| 交叉编译与 ELF / 裸二进制镜像                                                                | 目标代码的生成与装载                | **含义**：在 x86 主机上生成 RISC-V 64 位目标代码（`-mcmodel=medany`、`ld -m elf64lriscv`），再用 `objcopy -O binary` 去掉 ELF 头与符号表得到纯镜像。**关系**：两者都是可装载的目标产物，ELF 带元信息、裸镜像只有数据。**差异**：真实系统中内核与用户程序都以 ELF 被装载，由装载器解析程序头决定各段落点；本实验因为要落在固定物理地址，用裸 bin 更直接，而调试时仍使用带符号的 ELF（`bin/kernel`）。                           |
| `sp` 的初始化与内核栈                                                                     | 函数调用机制与栈帧                 | **含义**：RISC-V 的栈向低地址增长，`sp` 指向栈顶；`call` 用 `ra` 记录返回位置，被调用者保存寄存器压栈形成栈帧。**关系**：本实验是栈帧机制的第一次出场（`entry.S` 建栈加尾调用）。**差异**：这里只有一个执行流、只有一种栈，不存在进程与线程，也没有"用户栈与内核栈"之分；上下文切换需要保存与恢复整组寄存器并更换 `sp`，那是 lab4、lab6 的内容。                                                                                 |
| `ecall` 陷入 M 模式调用 SBI 服务                                                          | 系统调用与特权级切换                | **含义**：`ecall` 是受控的特权级提升指令，在 U 模式执行会陷入 S 模式（系统调用），在 S 模式执行会陷入 M 模式（调用固件服务）；两者都用固定寄存器传参（`a0`–`a7`）并用 `a0` 接收返回值。**关系**：调用形式完全同构，本实验相当于系统调用机制的一次预演。**差异**：服务提供者不同（M 模式固件与内核中的系统调用处理程序），SBI 调用不涉及地址空间切换、进程状态管理和参数合法性检查，而系统调用必须具备这些（lab5）。                                                   |
| OpenSBI 固件与其提供的 SBI 服务                                                            | 固件与引导程序（TRM / Bootloader） | **含义**：OpenSBI 是运行在 M 模式的固件，负责上电后的硬件初始化，并向上提供标准服务接口。**关系**：它的位置与职责同 OS 原理中的 BIOS/UEFI/引导程序相对应，启动日志中的 `Domain0 Next Address`、`Next Mode` 就是"交接"的体现。**差异**：传统 TRM 或引导程序在把控制权交给内核后基本退场，而 OpenSBI 常驻内存（实测占用区域为 0x80000000–0x8003ffff），内核运行期间可随时用 `ecall` 调用它——这正是 lab1 的 `cprintf` 有输出可用的原因。 |

#### 2. OS 原理中重要、但本实验没有对应上的知识点

lab1 只建立了"能启动、能输出"的最小环境，操作系统原理中大量核心机制尚未涉及：

1. **进程、线程与上下文切换**：本实验只有一条执行流（`kern_init` 的死循环），没有 PCB、没有 idle/init 线程，也不存在调度算法（对应 lab4、lab6）。
2. **虚拟内存与地址翻译**：没有页表、没有 MMU，代码中出现的 0x80200000 就是物理地址，不存在虚拟地址到物理地址的转换（lab2、lab4 引入分页，lab9 涉及页面置换与内存映射）。
3. **中断与异常处理**：没有 trap 入口、没有时钟中断、没有中断的开启与屏蔽，`kern/trap` 目录在本实验中还是空的（lab3）。
4. **用户态与完整的系统调用机制**：虽然使用了 `ecall`，但调用的是固件服务；还没有用户进程、没有 U 模式、没有系统调用的分发与参数检查（lab5）。
5. **同步与互斥**：单执行流不存在竞态问题，信号量、管程等概念无从体现（lab7）。
6. **文件系统与设备驱动**：`cons_init`、`kbd_intr`、`serial_intr` 均为空实现，输出直接借用固件能力，没有真正的驱动框架与文件系统抽象（lab8）。
7. **物理内存管理与分配算法**：内存布局由链接脚本静态写死，没有内存探测、没有页分配器与回收机制（lab2）。
8. **多核（SMP）与设备树**：boot ROM 中读取的 `mhartid` 表明硬件具备多核概念，但本实验仅使用单核，也未解析设备树。
9. **特权级保护与隔离**：内核与固件之间只有 S/M 两级协作，没有 U 模式、没有段页级权限检查与地址空间隔离。

### AI 协作开发的经验

本次实验中，AI 起到的作用是"加速定位问题 + 讲解底层机制"，但也有明确的使用边界，以下几点是实际体会：

1. **环境适配环节省下了大量时间。** 实验一开始就接连遇到 WSL 服务被禁用（`Wsl/0x80070422`）、启用功能后报 `HCS_E_SERVICE_NOT_AVAILABLE`、WSL 内用不了 Windows 的 localhost 代理、`make gdb` 找不到 `riscv64-unknown-elf-gdb`（需软链到 `gdb-multiarch`）等问题。AI 能依据报错给出诊断顺序，把原本需要反复检索的时间压缩到几分钟。
2. **最有价值的一次协作是定位"静默挂死"。** `make qemu` 打印完 OpenSBI 日志后毫无输出，也没有任何报错。AI 抓住了 `Domain0 Next Address : 0x0000000000000000` 这一行，指出这是固件版本差异导致启动参数语义变化：手册的 `-device loader` 写法对应旧版 OpenSBI（`fw_jump`，固定跳转 0x80200000），而本机 OpenSBI v1.3 属 `fw_dynamic`，需要通过 `-kernel` 显式提供下一阶段地址。改一处启动参数即解决。这次经历说明：**没有报错不等于没有问题，要回到工具自身的输出里找证据。**
3. **AI 的结论必须回到源码与实测验证。** 报告中的关键结论（`la` 展开为 `auipc` 加 `addi`、`tail` 编译为 `j`、`sp` 由 0x80046eb0 变为 0x80203000）全部来自反汇编与 GDB 单步实测，而不是 AI 的叙述；AI 提供的是"该看哪里"的方向，证据必须自己取。
4. **养成留存证据的习惯。** 把每一步的终端输出保存成文本（本次实验的 A、B 两份记录），写报告时只需整理粘贴，答辩时也有据可查。
