## 一、实验整体逻辑线

实验 3 的主线是"一次 trap 的完整生命周期"，它又被拆成三条相互衔接的子线索：**Trap 上下文保存与恢复 → Trap 入口与返回 → 中断与异常处理**。我们按"先把状态存下来，再把控制权交给 C，再按类型分流，最后原样还回去"的顺序推进：

1. **弄清楚被保存的是什么。** 中断发生的那一刻，CPU 的可见状态是 32 个通用寄存器加若干 CSR。`struct trapframe` 用 36 个 `uintptr_t` 槽位描述这份快照：`gpr[0..31]` 顺序对应 x0…x31，其后依次是 `sstatus`、`sepc`、`sbadvaddr`、`scause`。`SAVE_ALL` 已经把这份布局写死了，所以后续所有代码都只是"按偏移访问"。
2. **写出与之镜像的恢复代码（功能模块一上半）。** `RESTORE_ALL` 必须逆着 `SAVE_ALL` 做同样的事，且要处理两个不对称点：x0 恒为 0 不需要恢复；x2(sp) 在 `SAVE_ALL` 时是"先换栈再加偏移"的特殊处理，原值被藏在 `2*REGBYTES` 槽位里，因此必须在所有以 sp 为基址的加载完成之后再恢复。
3. **把控制权交给 C（功能模块一下半）。** `__alltraps` 在 `SAVE_ALL` 之后，此时 sp 正好指向 trapframe 的底部，于是 `move a0, sp` 就完成了"按调用约定传第一个参数"，`jal trap` 进入 C 世界；`trap()` 返回后顺序落入 `__trapret`，`RESTORE_ALL` 加 `sret` 回到被中断的指令流。
4. **在 C 里分流（框架给定的 `trap_dispatch`）。** `scause` 的最高位为 1 表示中断、为 0 表示异常，因此 `(intptr_t)tf->cause < 0` 就是"是否为中断"的判据，分别调用 `interrupt_handler` 与 `exception_handler`。
5. **实现两类处理语义（功能模块二）。** 中断侧：软件中断打印一行；时钟中断先 `clock_set_next_event()` 重新装载下一次事件，再累加 `ticks`，每 `TICK_NUM` 次打印一行统计，累计到 `SHUTDOWN_AFTER` 组后关机（避免无人值守时空转）；未知中断打印 cause 并 `print_trapframe`。异常侧：非法指令与断点按规定的格式打印，并把 `tf->epc` 推进实际指令长度；其余异常统一 `print_trapframe`。
6. **闭环验证。** 内核启动后 `idt_init()` 设好 `stvec`，`clock_init()` 装载第一次时钟事件，`intr_enable()` 打开 S 态全局中断，此后每 10 ms 触发一次时钟中断：`__alltraps → SAVE_ALL → trap() → trap_dispatch → interrupt_handler → RESTORE_ALL → sret`，`ticks` 稳定增长到 200，测试 3 通过；测试 1/2 则分别验证"寄存器上下文原样恢复 + 断点返回"与"非法指令返回 + 三类兜底输出"。

这条线的合理性在于：**每一步都是下一步的前提，而且每一步都可以独立观测**。没有正确的 trapframe 布局，`RESTORE_ALL` 就无从下手；没有 `move a0, sp`，C 侧拿不到参数，测试 1 的寄存器快照必然错乱；没有 `clock_set_next_event()`，`ticks` 永远停在 1；没有 `tf->epc += insn_length(...)`，`ebreak` 与非法指令会立刻再次陷入，形成死循环。反过来，只要这五环都成立，评分脚本要求的三段输出就会自然出现，不需要任何"为了通过测试而写的特判"。

### 2.1 `struct trapframe` 布局与 `SAVE_ALL`（框架原有，本次只读不写）

**负责人：贾钧涵-2412422（原理梳理）、雷帛霖-2412362（复核偏移）**

`SAVE_ALL` 做的事情可以逐条对上 trapframe 的槽位：

| 槽位 | 偏移 | 写入者 | 内容 |
| --- | --- | --- | --- |
| `gpr[0]` (zero) | `0*REGBYTES` | `STORE x0` | 恒 0，仍显式写入以保持布局整齐 |
| `gpr[1]` (ra) | `1*REGBYTES` | `STORE x1` | 返回地址 |
| `gpr[2]` (sp) | `2*REGBYTES` | `csrrw s0, sscratch, x0` 后 `STORE s0` | **被中断时的原 sp**（因为此时不能再用旧 sp 作基址） |
| `gpr[3..31]` | 对应偏移 | `STORE x3..x31` | 其余通用寄存器，逐个独立存放 |
| `status` | `32*REGBYTES` | `csrr s1, sstatus` | 陷入时的 S 态状态（此时 SIE 已被硬件清零） |
| `epc` | `33*REGBYTES` | `csrr s2, sepc` | 陷入指令/被中断指令的地址 |
| `badvaddr` | `34*REGBYTES` | `csrr s3, sbadaddr` | 访存类异常的出错地址 |
| `cause` | `35*REGBYTES` | `csrr s4, scause` | 本次 trap 的原因（最高位区分中断/异常） |

理解要点有三个：

1. **为什么 x2 要特殊处理。** 保存寄存器需要一块栈空间，而栈指针本身就是"被保存对象"之一。`SAVE_ALL` 先用 `csrw sscratch, sp` 把原 sp 暂存到 `sscratch`，再用 `addi sp, sp, -36*REGBYTES` 开新帧，最后用 `csrrw s0, sscratch, x0` 把原 sp 换进 `s0`、同时把 `sscratch` 清零。因此 `RESTORE_ALL` 不能像其它寄存器那样"用 sp 作基址读回 sp"，只能先读别的槽位、最后再恢复 sp。
2. **为什么 `sscratch` 被写成 0。** 本实验只发生在 S 态（没有用户态），S 态陷入时 `sscratch` 恒为 0 是一种约定：框架用这一点来区分"陷入来自 S 态"还是"来自 U 态"（U 态下 `sscratch` 通常保存内核栈指针）。这也是 `idt_init()` 里 `sscratch = 0` 的原因。
3. **为什么这份布局不能改。** `SAVE_ALL`、`struct trapframe`、`trap()` 签名都被框架锁定，`RESTORE_ALL` 与两个 handler 都只是这份布局的"读者"。一旦自行调整字段顺序，测试 1 的寄存器快照就会错位，而且错误极难定位——这正是实验强调"不要修改 `SAVE_ALL`"的原因。

### 2.2 `RESTORE_ALL`

**负责人：雷帛霖-2412362**

```asm
.macro RESTORE_ALL
    #lab3 function1 2412362
    # 先恢复两个 CSR：csrw 需要一个临时寄存器，如果放在 GPR 恢复之后会破坏已恢复的值。
    # 陷入时硬件已把 SIE 清零，因此这里写入的 sstatus.SIE 为 0，在恢复过程中不会重新开中断，
    # 真正的“是否开中断”由下面的 sret 依据 sstatus.SPIE 决定。
    LOAD s1, 32*REGBYTES(sp)
    csrw sstatus, s1
    LOAD s2, 33*REGBYTES(sp)
    csrw sepc, s2

    # x0 恒为 0，无需恢复
    LOAD x1, 1*REGBYTES(sp)
    LOAD x3, 3*REGBYTES(sp)
    LOAD x4, 4*REGBYTES(sp)
    ...
    LOAD x31, 31*REGBYTES(sp)
    # x2(sp) 最后恢复：上面的 LOAD 都以 sp 为基址，提前覆盖 sp 会读到错误的内存
    LOAD x2, 2*REGBYTES(sp)
.endm
```

三个设计决策及其理由：

- **CSR 先恢复，且借用 s1/s2 作临时寄存器。** `csrw` 必须经由一个通用寄存器完成。若把它放在 GPR 恢复之后，写 CSR 就要再多毁掉一个寄存器（或者从内存里再读一次，反而更绕）。s1/s2 在后面会被 `LOAD` 覆盖，所以"先用后覆盖"是零成本的。
- **x1、x3…x31 顺序随意，但基址必须仍是 trapframe 底。** 这些寄存器之间互不依赖，写在前面的值不会被后面的加载指令改写。
- **x2 放在最后。** 这是整个宏里唯一有硬性顺序要求的一条：所有偏移都相对 sp 计算，sp 一旦被改写，剩下的加载全部落到错误地址上。而原 sp 的值就在 `2*REGBYTES` 槽位里（`SAVE_ALL` 的对称设计），所以在最后一步把它读回来，帧就"刚好被拆掉"。

恢复完成后，`__trapret` 执行 `sret`：硬件用 `sepc` 重设 pc、用 `sstatus.SPIE` 重设 `SIE`、把特权级从 `sstatus.SPP` 恢复。由于 `exception_handler` 是通过修改 memory 里的 `tf->epc` 推进地址的，而 `RESTORE_ALL` 又是从 trapframe 里重新读 `sepc` 写回 CSR，所以"函数里改 epc"与"返回后跳转到下一条指令"能够自然衔接——这是本实验最关键的一处"内存中的状态 → 硬件中的状态"的转换。

### 2.3 `__alltraps`

**负责人：雷帛霖-2412362**

```asm
.align(2)
.globl __alltraps
__alltraps:
    SAVE_ALL
    #lab3 function1 2412362
    # 此时 sp 指向 trapframe 的底部，正好可以作为第一个参数传出去
    move a0, sp
    jal trap

.globl __trapret
__trapret:
    RESTORE_ALL
    sret
```

理解要点：

1. **`stvec` 指向 `__alltraps`，且必须是 4 字节对齐。** Direct 模式下 `stvec` 的低两位是模式位，BASE 部分要求 4 字节对齐，所以需要 `.align(2)`（2 的 2 次方 = 4 字节）。
2. **`move a0, sp` 是"调用约定的落地"。** RISC-V 调用约定第一个整型参数在 `a0`，而 `SAVE_ALL` 执行后 sp 恰好指向 trapframe 的首地址，因此一条 `move` 就把"寄存器快照"变成了"C 函数能读的 `struct trapframe *`"。换成"把地址写到某个全局变量再在 C 里读"也能工作，但违反约定且不可重入。
3. **`jal trap` 而不是 `call`/`tail`。** `jal` 会写 `ra`，但 `__alltraps` 不是被 `ret` 返回的函数，`ra` 在这里没有语义，只用来完成调用。`trap()` 返回后顺序执行到 `__trapret`（落穿），因此不需要 `j __trapret`。
4. **`trap()` 里面不会"返回两次"。** `trap()` 是普通 C 函数，返回时 sp 由被调用者自行恢复，仍等于 trapframe 底部，`RESTORE_ALL` 于是能读回完整快照。

### 2.4 `trap()` 与 `trap_dispatch()`

**负责人：贾钧涵-2412422**

```c
static inline void trap_dispatch(struct trapframe *tf) {
    if ((intptr_t)tf->cause < 0) {
        // interrupts
        interrupt_handler(tf);
    } else {
        // exceptions
        exception_handler(tf);
    }
}

void trap(struct trapframe *tf) {
    trap_dispatch(tf);
}
```

这两段是框架给定的，本次不修改，但它们是"分流语义"的落脚点：

- `scause` 用**最高位**编码"这是中断还是异常"：MSB=1 时低若干位是中断号（如 S 态定时器中断 5、软件中断 1、外部中断 9），MSB=0 时是异常号（如非法指令 2、断点 3、访存异常等）。
- 因此 `(intptr_t)tf->cause < 0` 恰好等价于"最高位为 1"，比 `tf->cause >> 63` 之类的写法更不易出错。
- 注意"中断"与"异常"只是 trap 的两个子类，二者共享同一条入口/返回路径，真正不同的只有处理语义——这也是为什么 `trap()` 本身可以薄到只有一行。

### 2.5 `interrupt_handler()`

**负责人：雷帛霖-2412362**

```c
void interrupt_handler(struct trapframe *tf) {
    intptr_t cause = (tf->cause << 1) >> 1;   /* 逻辑右偏移除最高位，得到中断号 */

    switch (cause) {
    case IRQ_S_SOFT:
        cprintf("Supervisor software interrupt\n");
        break;
    case IRQ_S_TIMER:
        clock_set_next_event();               /* 关键：先重装下一次事件 */
        ticks++;
        if (ticks % TICK_NUM == 0) {
            print_ticks();                    /* 框架函数：打印 "%d ticks" */
            if (ticks >= (size_t)TICK_NUM * SHUTDOWN_AFTER) {
                sbi_shutdown();               /* 打印足够多组后关机，避免空转 */
            }
        }
        break;
    default:
        cprintf("Unknown interrupt: cause %d\n", (int)cause);
        print_trapframe(tf);
        break;
    }
}
```

理解要点：

1. **`(tf->cause << 1) >> 1` 的作用。** 先左移把 MSB 挤出去，再逻辑右移补 0，得到去掉符号位的纯中断号。因为 `cause` 是 `uintptr_t`（无符号），两次移位都是逻辑移位，`<< 1 >> 1` 等价于 `& 0x7FFF...`，但对 64 位机型更直观、也不依赖立即数的位宽。
2. **时钟中断的"续命"必须是原子的、且在计数之前。** SBI 的定时器是"一次性"的：`sbi_set_timer(when)` 只在 `when` 到点时触发一次中断，处理完若不重装，就再也收不到下一次中断。把它放在 handler 的最前面还有一个好处：即使后面打印、关机等逻辑较慢，下一次事件的时刻也已经按"当前时间 + timebase"重新计算好了。
3. **`ticks` 的可见性。** `ticks` 被框架声明为 `volatile size_t`，因为它在中断上下文被写、在主流程被读；`volatile` 防止编译器把 `while (ticks < 200)` 优化成"只读一次"。
4. **`SHUTDOWN_AFTER` 是我们额外加的"安全阀"。** 指导书要求"每 `TICK_NUM` 次打印一次"，但没有说明打印多久后停。若不加限制，`make grade` 的测试 3 在 `timeout 30s` 之后会被杀掉，日志里会多出不确定的截断。我们选择打印 10 组（即 1000 个 tick）后调用 `sbi_shutdown()`，既满足"持续计时"的语义，又让无人值守的运行有确定终点。需要注意这**不影响**评分：测试 3 只要求出现 `100 ticks` 与 `ticks=200`。
5. **未知中断的兜底。** 打印 `Unknown interrupt: cause %d` 之后还要 `print_trapframe(tf)`，因为异常/未知中断发生后通常需要看现场；测试 2 会人为构造 cause=15 的中断来验证这条路径。

### 2.6 `exception_handler()` 与指令长度

**负责人：雷帛霖-2412362**

```c
static inline uintptr_t insn_length(uintptr_t epc) {
    uint16_t insn = *(volatile uint16_t *)epc;
    return ((insn & 0x3) == 0x3) ? 4 : 2;
}

void exception_handler(struct trapframe *tf) {
    switch (tf->cause) {
    case CAUSE_ILLEGAL_INSTRUCTION:
        cprintf("Illegal instruction at 0x%lx\n", tf->epc);
        tf->epc += insn_length(tf->epc);
        break;
    case CAUSE_BREAKPOINT:
        cprintf("Breakpoint at 0x%lx\n", tf->epc);
        tf->epc += insn_length(tf->epc);
        break;
    default:
        print_trapframe(tf);
        break;
    }
}
```

理解要点：

1. **异常返回必须"跳过"而不是"重试"。** 中断返回时 `sepc` 停留在"下一条未执行指令"，所以什么都不用改；而异常返回时 `sepc` 指向**出错的那条指令本身**（`ebreak` 或非法指令），若不推进，`sret` 回去后会立刻再次陷入，形成死循环。这是中断与异常在返回语义上的核心差异。
2. **长度必须按指令本身判断，不能写死 4。** RISC-V 的指令可以是 32 位，也可以是 16 位压缩指令（C 扩展）。判据是低两位：`!= 0b11` 即 16 位。在本实验的 RV64GC 环境里，`ebreak` 被汇编器编译成 16 位的压缩指令 `c.ebreak`（字节 `90 02`，共 2 字节）——把 `tools/test_lab3_context.S` 单独汇编后 `objdump` 可以看到 `6a: 9002  ebreak`，下一条指令在 `6c`；而测试 2 用手写的 `.word 0x0000007b` 构造非法指令（4 字节，且低两位恰为 `0b11`）。如果统一加 4，断点返回会跳过 `ebreak` 的下一条指令，测试 1 的寄存器校验就会失败；如果统一加 2，非法指令会落在 32 位指令的中间，触发 `misaligned` 之类的二次异常。
3. **长度读取必须放在两个 `case` 内部，不能提到 `switch` 之前。** `insn_length()` 会解引用 `epc`，而 `cause` 落在 `default` 分支时 `tf->epc` 未必是可执行地址——测试 2 的第三个场景用一个全零 trapframe 调用 `exception_handler`（cause=20/0x14），若在函数开头就读指令，会立刻触发"读地址 0"的访存异常，把一次可预期的兜底输出变成内核崩溃。这个约束在提示词里被明确写出（见第四章"问题 4"）。
4. **兜底只打印不推进。** 对无法识别的异常，`print_trapframe(tf)` 之后不做任何修改：既然不知道异常语义，就不该猜返回地址；保留现场交给调试者判断更安全。

### 2.7 时钟模块 `kern/driver/clock.c` 与 SBI

**负责人：贾钧涵-2412422**

- QEMU `virt` 机型上 `rdtime` 的频率是 10 MHz，即 `get_time()` 每 100 ns 增加 1。`timebase = 100000` 对应 10 ms，因此 100 个 tick 约 1 秒——这正是测试 3 用 `timeout 30s` 却只等 200 tick 的原因。
- `clock_set_next_event()` 的实现是 `sbi_set_timer(get_time() + timebase)`：把"下一次事件的绝对时刻"交给 M 态固件（OpenSBI），由固件在到点时置位 S 态定时器中断（`scause = 0x8000...05`）。
- `clock_init()` 做四件事：`sie |= MIP_STIP` 打开 S 态定时器中断源、`clock_set_next_event()` 装载第一次事件、`ticks = 0`、打印 `++ setup timer interrupts`。注意此时全局中断还没开（`intr_enable()` 在后面），所以第一次中断会"等到" `intr_enable()` 之后才真正到来。
- 一条容易踩的坑：`ticks` 必须在 `intr_enable()` 之前被清零。测试 3 的 `test_lab3_timer_is_armed()` 会在开中断前检查 `ticks == 0`，若不为 0 会给出警告——这提示"计时从 0 开始"是被显式验证的语义。

### 2.8 中断使能链路 `kern/driver/intr.c` 与 `libs/riscv.h`

**负责人：贾钧涵-2412422**

- `intr_enable()` = `csrs sstatus, SSTATUS_SIE`，`intr_disable()` = `csrc sstatus, SSTATUS_SIE`，只操作 S 态全局中断开关，不碰 `sie`/`sip` 里的具体中断源。
- 一次时钟中断真正"被投递"需要三层同时满足：`sie` 中该中断源被使能、`sstatus.SIE` 被置位、且（在本实验的单核环境下）没有更高优先级的中断挂起。因此 `idt_init → clock_init → intr_enable` 的顺序不是随意的。
- `idt_init()` 在 `kern_init` 中被调用两次（`pmm_init` 前后各一次）。从代码看两次写入的 `stvec`/`sscratch` 值相同，重复调用是"防御性"的：一是让 `stvec` 在开启页表（`pmm_init` 改变 `satp`）前后都指向正确的虚拟地址，二是 `kern_init` 阶段若有意外陷入（比如 `pmm_init` 期间的断言失败），也能走统一的 trap 路径。

### 2.9 同步与原子性：`sync.h`、`atomic.h`（与 lab2 代码回填的耦合）

**负责人：贾钧涵-2412422**

- `kern/sync/sync.h` 提供 `__intr_save()`（读 `sstatus` 并关中断，返回旧值）与 `__intr_restore(flags)`（写回旧值），`local_intr_save(x)` 则被定义成 `do { x = __intr_save(); } while (0)`。
- `kern/mm/pmm.c` 的 `alloc_pages()/free_pages()` 用 `local_intr_save/restore` 包住对 `pmm_manager` 的调用，保证"检查空闲链表 + 摘除节点"这对操作不会被时钟中断打断；`kern/mm/memlayout.h` 的 `SetPageReserved` 等宏改用 `libs/atomic.h` 的 `set_bit/clear_bit/test_bit`，把"读—改—写"三步压成单条原子指令（`amoor.w` 等）。
- 这一点与 lab2 代码的回填直接相关：lab3 骨架里 `best_fit_pmm.c`、`pmm.c` 是空缺的，而 lab3 的 `memlayout.h` 已经把页标志位换成了原子位操作。因此回填时必须用 lab2 的**算法**、lab3 的**头文件语义**，不能把 lab2 的整份文件覆盖过来（否则要么编译不过，要么绕过原子操作）。

### 3.2 功能模块一（`trapentry.S`）的 spec 与 prompt

**spec 摘要：** 在 `SAVE_ALL` 之后补全 `__alltraps`（把 trapframe 地址按 RISC-V 调用约定作为第一个参数传给 `void trap(struct trapframe *)`，返回后落入 `__trapret`），并实现 `RESTORE_ALL`（与 `SAVE_ALL` 完全镜像地恢复 32 个通用寄存器与 `sstatus`/`sepc`；x0 不需恢复；x2 必须最后恢复）。不得修改 `SAVE_ALL`、`struct trapframe`、`trap()` 签名。

**spec 摘要：** 实现 `interrupt_handler()` 与 `exception_handler()`：S 态软件中断打印 `Supervisor software interrupt`；时钟中断重装下一次事件、累加 `ticks`、每 `TICK_NUM` 次调用 `print_ticks()`、累计 `SHUTDOWN_AFTER` 组后 `sbi_shutdown()`；未知中断打印 `Unknown interrupt: cause %d` 并 `print_trapframe`；非法指令打印 `Illegal instruction at 0x%lx` 并推进 `epc` 实际指令长度；断点打印 `Breakpoint at 0x%lx` 并同样推进；其余异常 `print_trapframe`。

**prompt 摘要（全文见附录 A.2）：**

### 3.4 三条写法原则

1. **先给约束，再给代码。** 把"不能改什么"（`SAVE_ALL`、签名、框架函数）写在最前面，比事后审查 AI 有没有擅自"优化"更省力。
2. **把验收标准写成可执行断言。** 例如"`while (ticks < 200)` 能退出""日志里出现 `cause    0x00000014`"，这样 AI 的产出可以直接交给 `make grade` 判定，而不是靠人眼读代码。
3. **把已知的坑写成显式禁止项。** 例如"不要假设指令长度为 4""不要在 `switch` 之前读 `epc`"，这些正是本实验最容易出现的隐性 bug，写进 prompt 后 AI 一次就避开了。

### 问题 2：内核没有被 QEMU 真正加载，串口只有 OpenSBI 横幅

**现象：** 合并完成后编译成功，但评分仍全 0。抓取串口日志发现输出停在 OpenSBI 横幅：

```
Domain0 Next Address      : 0x0000000000000000
```

之后再无 `(THU.CST) os is loading ...`。正常情况下这一行应该是 `0x0000000080200000`。

**原因（分析）：** 两件事叠加。

1. `grade.sh` 用 `-device loader,file=bin/ucore.img,addr=0x80200000` 的方式装载内核。这种写法在 QEMU 4.x 时代是有效的（固件会跳到 `0x80200000`），但 QEMU ≥ 5 附带的是 `fw_dynamic` 固件，`-device loader` 只把镜像"塞进内存"，并不会告诉固件从哪里开始执行，于是 `Domain0 Next Address` 变成 0，CPU 跳进空地址后静默停住。
2. 课程环境用 `/oslab/riscv/bin/qemu-system-riscv64` 这个 1478 字节的**包装脚本**解决上述问题：它把 `-device loader,file=X,addr=0x80200000` 改写成 `-kernel X`，让固件跳转到镜像入口。但 PATH 里 `/usr/bin` 排在前面，`grade.sh` 实际调用的是 `/usr/bin/qemu-system-riscv64`（真正的 15 MB QEMU 6.2 二进制），包装脚本压根没生效。

**解决：** 在运行评分脚本前 `export PATH=/oslab/riscv/bin:$PATH`，确保调用的是包装脚本。之后日志立刻正常：

```
Domain0 Next Address      : 0x0000000080200000
DTB Address: 0x87000000
(THU.CST) os is loading ...
memory management: default_pmm_manager
check_alloc_page() succeeded!
```

**教训：** "编译通过 + 输出只有固件横幅"是一个很典型的"镜像没跑起来"特征，与内核代码无关。判断方法就是看 `Domain0 Next Address` 是否等于链接地址（本实验为 `0x80200000`）。

### 问题 4：指令长度计算的边界风险（AI 初版写法会把风险带进 `epc = 0` 的路径）

**现象（审查阶段发现，未进入最终代码）：** 让 AI 写 `exception_handler` 时，它给出的初版是"先算长度、再进 switch"：

```c
uintptr_t len = insn_length(tf->epc);   /* ← 危险：任何异常都先解引用 epc */
switch (tf->cause) { ... }
```

**原因（分析）：** 这个写法在"真实异常"下没问题，但测试 2 的第三个场景是**人造**的：它 `memset` 出一个全零 trapframe（`epc = 0`），直接调用 `exception_handler(tf)` 并把 `cause` 设成 20（0x14），只为验证"未知异常走 `print_trapframe` 兜底"。若在函数开头解引用 `epc = 0`，会立刻触发一次额外的访存异常，兜底输出根本走不到，测试 2 直接失败。此外从语义上看，"未知异常"本来就不该假设 `epc` 指向一条合法指令。

**解决：** 把 `insn_length()` 的调用严格放进 `CAUSE_ILLEGAL_INSTRUCTION` 与 `CAUSE_BREAKPOINT` 两个 `case` 内，并在 prompt 里把"不要在 switch 之前读取 epc"写成硬约束（见附录 A.2 的 `[SPECIFICATION]` 第 6 条）。

**教训：** AI 很容易给出"看起来更整洁"的早期求值写法。判断标准不是美观，而是**每条路径上的前提是否成立**：读 `epc` 的前提是"这是一个确实由取指/执行失败的指令引发的异常"，而这个前提只在两个具体 cause 下成立。

### 5.3 两个思考题

**（1）`kern/sync/sync.h` 中 `local_intr_save(x)` 为什么用 `do { x = __intr_save(); } while (0)` 包一层？**

- **让它表现得像一条语句。** 宏展开后是"声明 + 赋值"两条语句（`x = ...;` 至少一条），若直接写成 `#define local_intr_save(x) x = __intr_save()`，那么 `if (cond) local_intr_save(flags); else ...` 会因为多出分号而语法错误，或者被 `if` 错误地"只包住第一条"。`do { } while (0)` 让整块成为一个需要分号的单条语句，可以安全地出现在任何需要语句的位置。
- **避免悬空 else / 多语句宏的通病。** 这是 C 语言里最经典的两个宏陷阱（另一个是 `#define sq(x) x*x` 的优先级问题），`do { } while (0)` 同时解决"无分号结尾"和"语句边界"。
- **`while (0)` 不会产生额外运行时开销**：编译器会直接把它优化成顺序执行，`break`/`continue` 语义也被限制在块内，不会跳到外层循环。
- 顺带一提：如果只赋值给一个已声明变量（没有声明语句），用逗号表达式 `((x) = __intr_save())` 也能工作，但 `do{}while(0)` 是更通用、更易读的写法，`local_intr_restore` 以及内核里大量"多语句宏"都用同一套写法。

**（2）stvec 的 Vectored 模式是 1.10 版才加入的，这个改动如何保证后向兼容？**

- 旧版（privileged spec 1.9.1 及以前）只定义了 Direct 模式：`stvec` 的低两位被视为 0，BASE 直接就是入口地址。新版把低两位定义为 MODE 字段（00=Direct，01=Vectored），并且**要求 Direct 模式下这两个位必须写 0**。
- 因为旧软件的 `stvec` 写入值天然满足"4 字节对齐"（BASE 的低两位本来就是 0），所以这些值在新版解码时 MODE=00，语义仍是 Direct——旧二进制无需重新编译即可继续运行，这就是后向兼容的来源。
- 代价是入口地址必须 4 字节对齐（本实验的 `.align(2)` 正是为此），以及 Vectored 模式下入口表按"4 字节 × cause 号"排列，中断向量表不再是"一段代码"而是"一个跳转表"。
- 新版还规定：Vectored 模式只对**中断**生效，异常仍然跳到 BASE；若某些实现把 `cause` 号当作索引用，需要注意表项数量与 `MAX_CAUSE` 的对应关系。

## 六、知识点与 OS 原理的对应

### 6.1 对照表

| 实验中的知识点 | 对应的 OS 原理 | 含义、关系与差异 |
| --- | --- | --- |
| `struct trapframe` + `SAVE_ALL/RESTORE_ALL` | 进程上下文切换（context switch） | trapframe 是"陷入现场的镜像"，上下文切换是"换掉整个执行流"。前者保存到**本执行流的栈**上、很快恢复；后者要保存到 PCB/内核栈、换栈、可能换地址空间。本实验只做前者，是后者的必要组成部分 |
| `stvec` + `__alltraps` | 中断/异常向量表（IDT / 异常表） | RISC-V 用单个 `stvec` + 软件分发，x86 用中断描述符表（IDT）逐向量登记处理函数。前者入口统一、靠 `scause` 二次分发；后者硬件直接定位处理函数，开销更小但表更大 |
| `scause` 最高位分流 | 中断与异常的区分（异步/同步） | 中断由外部事件异步触发、返回地址是"下一条未执行指令"；异常由当前指令同步触发、返回地址是"出错指令本身"。这一差异直接决定了 handler 里要不要推进 `epc` |
| `tf->epc += insn_length(...)` | 异常恢复与指令重试/跳过 | "跳过"是因为本实验把非法指令与断点当作"可继续"的异常；真实内核里缺页异常的处理恰恰相反——修好页表后**重试**原指令（`epc` 不变），这是同一机制下的两种用法 |
| `clock_set_next_event()` | 时钟中断/时间片轮转的基础 | 一次性定时器必须每次重装，这正是"时间片"能持续产生的原因；真实 OS 在这一步之后会做调度决策（本实验只计数） |
| `ticks`、`TICK_NUM` | 系统时间/jiffies、tick 与调度周期 | `ticks` 就是内核的 jiffies 雏形：一个在中断上下文累加的全局计数器，供超时、延时、统计使用。`TICK_NUM` 对应"每 N 个 tick 做一次周期性工作"的节拍概念 |
| `local_intr_save/restore` + `set_bit/test_bit` | 临界区、中断屏蔽、原子操作 | 单核上"关中断"是足够强的互斥手段；多核则不足（需要自旋锁/原子指令）。`local_intr_save` 保存旧状态再恢复，是为了支持嵌套临界区——这是"可重入的关中断"设计 |
| `sscratch` 的用法 | 用户态/内核态栈切换 | 本实验只在 S 态，`sscratch = 0` 仅作标记；真正的 OS 在 U→S 陷入时用 `sscratch` 换到内核栈（`csrrw sp, sscratch, sp`），这是"每进程内核栈"的实现基础 |
| `sret` 与 `sstatus.SPIE/SPP` | 特权级返回与中断嵌套 | `sret` 不是简单跳转：它同时恢复特权级与中断使能位。这意味着"返回"本身是一次状态迁移，嵌套中断的恢复必须依赖这套硬件语义 |
| `sbi_set_timer` / `sbi_shutdown` | 固件与内核的接口（SBI） | 内核不直接操作 M 态定时器/关机，而是通过 ecall 请求固件代劳。这对应"硬件抽象层/固件接口"的思想：把特权操作收敛到最小接口，内核只依赖 ABI |
| `#ifdef DEBUG_GRADE` 的 `print_ticks` | 编译期开关与测试桩 | 同一份代码在"评分模式"下打印 `End of Test.` 并 `panic`，在正常模式下只打印 tick。这对应 OS 里的调试开关（`CONFIG_*`）与断言/panic 机制 |

### 6.2 OS 原理中重要、但本实验未覆盖的知识点

1. **用户态与系统调用（U 模式、`ecall` 的完整往返）。** 本实验全程在 S 态，没有 U 态进程，也没有 `ecall from U-mode → 系统调用分发 → 返回用户态`的链路；`sscratch` 的栈切换技巧因此没有被真正用到。
2. **进程/线程与调度。** 时钟中断只做了计数，没有触发调度器；`trapframe` 与 PCB/内核栈的关系、`switch_to`、就绪队列、时间片与优先级都没有涉及。
3. **缺页异常与按需分页。** 实验里的异常只处理非法指令与断点，`badvaddr` 只被打印。真正的缺页处理（判断地址合法性、分配页、填页表、重试指令）是 lab2 页表与 lab3 异常机制的结合点。
4. **中断嵌套与优先级。** 本实验的 handler 不做抢占，也没有"高优先级中断打断低优先级 handler"的场景；`sstatus.SIE` 在陷入时被硬件清零，其实天然屏蔽了同优先级中断，这与 Linux 的 `irqsave/irqrestore` 语义一致但实验未展开。
5. **外设中断与 PLIC。** 只有软件中断与定时器中断，没有外部中断（UART/磁盘/网卡）的"中断控制器 → 使能 → 认领 → 完成（EOI）"流程。
6. **多核与中断亲和性。** 单 hart 环境，没有核间中断（IPI）、没有每核独立的中断状态、也没有内存序问题。
7. **锁与并发控制。** 只有"关中断"这一种手段，没有自旋锁、信号量、睡眠唤醒；`atomic.h` 的位操作也只用于页标志。
8. **异常/中断的性能与安全。** 例如内核栈溢出保护、`stvec` 被攻击者篡改、Spectre 类侧信道与中断时间的关系——这些属于系统安全范畴，实验不涉及。

### 6.3 AI 协作开发的经验

1. **先让 AI 复述约束，再让它写代码。** 我们在 prompt 里要求"先用三条话总结你不能修改哪些东西"，确认它读懂了 `SAVE_ALL`/`trap()` 的不可变性，再让它动手。这一步比事后 review 便宜得多。
2. **把"环境问题"和"代码问题"分开归因。** 本实验前两次 0 分都不是 lab3 代码的错（一次是骨架缺 lab2 代码，一次是 QEMU 包装脚本没生效），第三次才是注入问题。"日志停在固件横幅"这种特征，AI 很容易误判成"内核 panic 了"，我们靠"看 `Domain0 Next Address` 是否等于链接地址"这条硬判据纠正了它。
3. **让评分脚本成为唯一裁判。** 人工读代码只能证明"看起来对"；`make grade` 的三段字符串 + 寄存器快照才是可复现的验收。我们把评分流程封装成脚本（复制到 `/tmp`、注入、评分、抓串口日志），每改一次代码跑一次，避免"改 A 坏 B"。
4. **对 AI 的"整洁优化"保持怀疑。** 问题 4 就是典型：把长度计算提到 `switch` 之前，代码更短更"优雅"，但破坏了"未知异常不得假设 epc 合法"的前提。判断标准永远是路径前提，不是代码形态。
5. **把踩过的坑写回 prompt 与文档。** 例如"不要假设指令长度""不要在 switch 前读 epc""QEMU 需用兼容包装脚本"，这些结论沉淀进附录 A 的 prompt 与第九章的适配说明后，后续同类任务的成功率明显提高。

## 七、思考题与扩展

### 7.1 `local_intr_save` 中的 `do { } while (0)`

见 5.3(1)。要点：让多语句宏成为单条语句、避免 `if/else` 悬空、`while (0)` 零开销、块内 `break/continue` 不影响外层。

### 7.2 stvec 向量表模式的后向兼容

见 5.3(2)。要点：旧版把低两位当"保留的 0"，新版把它们定义为 MODE；旧软件的 4 字节对齐地址天然解码为 Direct，因此二进制兼容；代价是入口必须 4 字节对齐、Vectored 只作用于中断。

### 7.3 关于 Challenge 与分支任务

lab3 的指导书没有设置 Challenge，也没有分支任务（只有上述两个思考题）。如果要把 lab3 继续做深，我们认为有三个自然的延伸方向：

1. **Vectored 模式改写。** 把 `stvec` 的低两位设为 01，构造一个按 cause 索引的跳转表，只让定时器中断走向量入口，其余仍回落到统一入口——正好可以验证 7.2 的"只作用于中断"这一条。
2. **把时钟中断接到调度。** 在 `ticks % TICK_NUM == 0` 时切换一个"伪线程"（两份 trapframe 交替恢复），就能在不引入完整进程管理的前提下观察"时钟中断 → 上下文切换"的最小闭环。
3. **`ecall` 系统调用雏形。** 用 `CAUSE_USER_ECALL`/`CAUSE_SUPERVISOR_ECALL` 分支，把 `a7` 当调用号、`a0..a5` 当参数，实现一个最简 `sys_write`，把 `trapframe` 从"中断镜像"扩展成"系统调用参数载体"。

### A.3 追加追问（实际使用）

- "为什么 RESTORE_ALL 里 sstatus 要放在 sepc 之前恢复？如果反序会怎样？"（回答：写入 sstatus 可能改变 SIE，虽然陷入时已被清零，但把"状态恢复"集中在前、把"地址恢复"紧随其后更安全，也不依赖顺序假设。）
- "把 `insn_length` 提到 switch 前面为什么不行？"（回答见第四章问题 4。）
- "时钟中断不重新装载会出现什么现象？"（回答：只收到一次中断，`ticks` 停在 1，测试 3 的 `while (ticks < 200)` 永不退出，被 `timeout` 杀掉。）
