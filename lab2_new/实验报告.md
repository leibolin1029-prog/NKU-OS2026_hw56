## 一、实验整体逻辑线

本实验在 lab1 最小可执行内核的基础上完成两件事：**打开 Sv39 分页**、**建立物理内存管理**。整体按"先有地址空间、再谈内存管理"的顺序推进：

1. **改造链接与启动（让内核具备虚拟地址）**
   `tools/kernel.ld` 的 `BASE_ADDRESS` 由 `0x80200000` 改为 `0xFFFFFFFFC0200000`，链接器据此为所有符号分配虚拟地址；但 OpenSBI 交权时 CPU 处于 S 模式、`satp` 为 Bare（直译物理地址），若直接执行就会跳到"物理上不存在的虚拟地址"。因此 `kern/init/entry.S` 在入口处构造启动页表、写入 `satp`、执行 `sfence.vma`，之后才用虚拟地址设置栈指针并跳入 `kern_init`。这一步解决了"内核运行在哪个地址空间"的问题。

2. **发现物理内存（先知道内存有多少）**
   物理内存布局由 OpenSBI 扫描后以 DTB（设备树）形式交给内核，地址放在 `a1` 寄存器中。`entry.S` 把 `a0`（hartid）与 `a1`（DTB 地址）存入全局变量，`kern_init` 调用 `dtb_init()` 解析 `memory` 节点的 `reg` 属性，得到物理内存的起始地址与长度。没有这一步，后续无法知道该管理哪些页。

3. **建立页描述符布局（把物理内存"登记造册"）**
   `pmm_init()` 依次调用 `init_pmm_manager()`、`page_init()`、`check_alloc_page()`。其中 `page_init()` 是本次实验的第一个核心任务：读取设备树结果，确定可管理页号上界，在内核镜像之后铺一张 `struct Page` 描述符数组，先把所有页标记为保留，再把"描述符数组之后、内存末端之前"的完整页区间交给当前物理内存管理器。

4. **实现并接入分配算法（真正能分配）**
   框架以 `struct pmm_manager` 抽象出分配器接口，`default_pmm.c` 提供 First-Fit 参考实现。本次实验的第二个核心任务是在 `best_fit_pmm.c` 中实现 Best-Fit（在满足 `property >= n` 的空闲块中选择最小者），并把 `init_pmm_manager()` 切换为 `best_fit_pmm_manager`。切换完成后 `check_alloc_page()` 实际校验的就是 Best-Fit 的行为。

5. **扩展挑战（可选）：Buddy System**
   在同样的 `pmm_manager` 抽象下实现按 2 的幂分块、支持分裂与伙伴合并的分配器，并自行设计测试函数验证其正确性。

这样安排的合理性在于：**地址空间 → 内存范围 → 页描述符 → 分配算法**，每一环都是下一环的前提；跳过任何一步，后面的检查都会立刻失败。

## 二、核心函数与功能模块的理解

### 2.1 `kern/init/entry.S`：建立启动页表并切换到虚拟地址

入口处依次完成：保存 `a0`/`a1`；计算启动页表的物理页号；把 `satp` 的 MODE 字段设为 Sv39（`8 << 60`）并写入页表页号；`sfence.vma` 刷新 TLB；用虚拟地址设置 `sp` 并跳转到 `kern_init`。

启动页表只有一页（512 个页表项）：索引 511 映射 `0xFFFFFFFFC0000000 → 0x80000000`（1 GiB 大页），索引 2 额外建立 `0x80000000 → 0x80000000` 的恒等映射。**恒等映射是本次实验中定位到的关键点**：`csrw satp` 之后分页立即生效，而程序计数器仍停留在物理地址上，若没有低地址段的映射，后续取指会触发指令页错误（详见第四章）。

### 2.2 `kern/driver/dtb.c`：物理内存探测

`dtb_init()` 校验 DTB 魔数 `0xd00dfeed`，然后按 FDT token（`FDT_BEGIN_NODE` / `FDT_PROP` / `FDT_END_NODE`）遍历结构块，在名为 `memory` 的节点中取出 `reg` 属性，得到物理内存的 base 与 size，存入静态全局变量供 `page_init()` 通过 `get_memory_base()`、`get_memory_size()` 读取。QEMU virt 平台的结果为 base = `0x80000000`、size = `0x8000000`（128 MiB）。

### 2.3 `kern/mm/pmm.c: page_init()`：建立页描述符布局（核心任务一）　**负责人：雷帛霖-2412362**

职责可概括为三句话：**定偏移、铺数组、划空闲区**。

- `va_pa_offset = PHYSICAL_MEMORY_OFFSET`，确定虚实地址换算关系；
- `npage = PPN(mem_base + mem_size)`，得到可管理页号上界（注意是页号，不是字节数除以页大小）；
- `pages = ROUNDUP(end, PGSIZE)`，描述符数组紧接内核镜像并按页对齐；
- 对 `[nbase, npage)` 的每个页清零 `flags/property/ref` 并置 `PG_reserved`；
- 起点 `PADDR(ROUNDUP(pages + (npage - nbase), PGSIZE))` 向上对齐、终点 `ROUNDDOWN(mem_base + mem_size, PGSIZE)` 向下对齐，两者之间非空时调用 `init_memmap()` 注册空闲区。

设计上有四个必须坚持的约定：

1. **下标与页号的换算**：描述符数组按页号排列，数组下标为 `PPN - nbase`，因此 `pa2page()`、`page2pa()` 都带 `nbase` 偏置；
2. **先保留后接管**：布局完成前若允许分配，未初始化的页会被当作空闲页交出；且 `init_memmap()` 内部逐页断言 `PageReserved`，因此保留位必须由 `page_init()` 设置、由管理器在接管时清除；
3. **虚拟地址与物理地址不可混用**：`pages`、`end` 是虚拟地址，与 `mem_base/mem_size` 比较前必须 `PADDR()`；
4. **只交出完整页**：两端按页对齐后中间若有不足一页的尾部，直接丢弃。

### 2.4 `kern/mm/best_fit_pmm.c`：Best-Fit 分配器（核心任务二）　**负责人：雷帛霖-2412362**

内部状态与 First-Fit 相同：一个 `free_area_t`（按地址升序的空闲块链表 + 空闲页总数），块头的 `PG_property` 置位、`property` 记录块长。

- `best_fit_init`：链表置空、`nr_free = 0`；
- `best_fit_init_memmap`：逐页断言 `PageReserved` 后清标志、`ref = 0`；`base->property = n` 并置位；按地址有序插入；`nr_free += n`；
- `best_fit_alloc_pages`：`n > nr_free` 直接失败；遍历链表记录 `property >= n` 的**最小块**；命中后从链表摘除，若块长大于请求则切出剩余块（`page + n`、长度相减、置位）并插回原位置；`nr_free -= n`；清除被分配块头的 `PG_property`；
- `best_fit_free_pages`：逐页断言"非保留且非空闲块头"（防重复释放）；组成新块后按地址插回；先后向合并（`p + p->property == base`）再后向合并（`base + base->property == p`），合并时清除被并入方的标志并摘链；
- `nr_free_pages`：返回计数。

与 First-Fit 的唯一本质差异是 `alloc_pages` 的选块策略（最小够用 vs 第一个够用），其余结构与合并逻辑完全一致。

### 2.5 `kern/mm/buddy_pmm.c`：Buddy System（Challenge）　**负责人：雷帛霖-2412362**

以阶（order）组织空闲块：`free_lists[BUDDY_MAX_ORDER]`，块大小 `2^order` 页，块头 `property` 记录阶数；`nr_free` 为所有阶的页数之和。

- 分配：把请求向上取整到 `2^k`，从最小可用阶取块并逐级分裂（右半块挂入低一阶）；
- 释放：按 `2^k` 归还，伙伴页号为 `idx XOR 2^k`，同阶且空闲则合并，并继续向上一阶尝试；
- 自检 `buddy_check()`：校验块头标志与阶数、块起点对齐、各阶页数之和等于 `nr_free`、块之间不重叠。

### 2.6 管理器抽象 `struct pmm_manager`

六个函数指针（`init`、`init_memmap`、`alloc_pages`、`free_pages`、`nr_free_pages`、`check`）把"算法"与"调用方"解耦：`pmm.c` 中的 `alloc_pages()` 等只是转发，切换实现只需改 `init_pmm_manager()` 中的一次赋值。这也是本次实验能同时容纳 First-Fit、Best-Fit、Buddy 三种实现的原因。

## 四、AI 生成代码过程中的问题与解决

### 问题 1：`best_fit_pmm.c` 缺空闲区定义导致编译失败

现象：`make` 报 `'free_list' undeclared`、`'nr_free' undeclared`（`basic_check` 与 `best_fit_check` 中），`make grade` 因编译失败输出 `no $qemu_out`、`Total Score: 0/20`。

原因：`free_list`/`nr_free` 由 `default_pmm.c` 中的 `static free_area_t free_area` 与两个宏定义，`static` 作用域限于单个编译单元；而框架提供的检查函数位于 `best_fit_pmm.c` 内并直接引用这两个名字，因此该文件必须自行定义空闲区状态。

解决：在 `best_fit_pmm.c` 顶部补 `static free_area_t free_area;` 与两个宏，并实现五个接口函数；编译恢复。

### 问题 2：内核启动无任何输出（指令页错误）

现象：改用 `-kernel` 启动后，串口只输出 OpenSBI 日志，内核没有任何输出；QEMU 异常日志反复出现：
`cause:0x0000000c (exec_page_fault), epc:0x80200038, tval:0x80200038`。

定位：`objdump -d bin/kernel` 显示 `0x80200034` 是 `csrw satp,t0`、`0x80200038` 是紧随其后的 `sfence.vma`。

原因：启动页表只映射了高地址段（索引 511）。`csrw satp` 写入后分页立即生效，但 PC 仍为物理地址 `0x80200038`；硬件把该物理值当作虚拟地址查表，索引 2 为空（`V = 0`），取指失败并进入"陷入—返回入口—再次失败"的循环。手册写作时代的 QEMU 会把 `csrw` 之后的若干指令保留在同一翻译块内执行，因此该问题不显现；QEMU 8.2 在 `csrw satp` 处重新取指，问题暴露。

解决：在 `boot_page_table_sv39` 中为索引 2 增加恒等映射 `(0x80000 << 10) | 0xcf`，页表仍为 512 项（`8*2 + 1 + 8*508 + 1`，共 4 KiB）。修改后内核正常输出 DTB 信息并完成 `pmm_init`。

### 问题 3：启动参数与固件版本不匹配

现象：使用手册给出的 `-device loader,file=...,addr=0x80200000` 时，OpenSBI 日志显示 `Domain0 Next Address : 0x0000000000000000`，随后静默挂死。

原因：该写法依赖旧固件（`fw_jump`，跳转地址编译期固定为 `0x80200000`）；QEMU 8.2 自带 OpenSBI v1.3（`fw_dynamic`），需要引导方显式提供下一阶段地址。

解决：`Makefile` 的 `qemu`、`debug`、`test` 目标与 `tools/grade.sh` 的 `qemuopts` 改用 `-kernel`，`Domain0 Next Address` 变为 `0x80200000`。

### 问题 4：自测函数的假设错误

现象：`buddy_test` 的碎片测试在 `assert(alloc_pages(8) == NULL)` 处断言失败。

分析：该断言假设"碎片化后系统整体无法满足 8 页请求"，但空闲内存有数万页，其他空闲块足以满足该请求——分配成功是正确行为，错的是测试假设。

解决：改为检查被切碎区块的可观测状态：`PageProperty(blk) && blk->property == 2`（4 页块为 order 2）、归还后 `blk->property == 3`（合并回 order 3）。教训是：AI 生成的测试同样可能出错，出现断言失败时应先区分是实现错误还是测试假设错误。

## 五、练习解答

### 5.1 功能模块一 思考题：OS 如何获得可用物理内存范围

若操作系统无法提前获知硬件内存布局，应通过**引导程序移交的硬件描述信息**获取。在 RISC-V 平台上标准做法是设备树（DTB）：OpenSBI 扫描外设后将结果以扁平设备树形式放在内存中，并把地址放在 `a1` 寄存器中传给内核；内核解析 `memory` 节点的 `reg` 属性即可得到物理内存的起始地址与长度（本实验 `dtb.c` 即此实现）。其他平台的对应机制包括 x86 的 BIOS `INT 15h/E820`、ACPI 内存映射表、ARM 的 ATAGS 或 UEFI 内存描述表等。若完全没有固件信息，也可采用"试探法"（逐段读写探测可用范围），但可靠性差、实现复杂，实际系统不采用。

### 5.2 功能模块二 任务一：First-Fit 的实现与改进空间

`default_pmm.c` 的四个函数：

- `default_init`：链表置空、`nr_free = 0`；
- `default_init_memmap`：逐页断言保留、清标志与引用计数，`base->property = n` 并置位，按地址有序插入，`nr_free += n`；
- `default_alloc_pages`：从头扫描，取第一个 `property >= n` 的块；若块长大于请求则从头部切出 `n` 页，剩余块插回原位置；`nr_free -= n`，清除块头标志；
- `default_free_pages`：校验后组成新块、按地址插回，并向前、向后各合并一次相邻空闲块。

改进空间：

1. **扫描成本**：每次分配都从链表头线性扫描（O(空闲块数)），可维护按尺寸排序的分离空闲链表，或加索引加速查找；
2. **碎片问题**：首次适应会反复切碎大块，产生外部碎片；可采用下次适应（next-fit）分散切碎位置、最优适应（best-fit）减少剩余碎片，或引入位图/Buddy 等结构；
3. **合并时机**：只在释放时合并，可考虑延迟合并或空闲块按位图管理，降低频繁分配释放时的链表维护开销。

实现见 2.4 节；实验结果见第七章验证记录（`[Test 2] Best-Fit: PASS`）。测试函数 `basic_check` 与 `best_fit_check` 未作任何修改，实现只新增在标记位置与文件末尾的注册处。

## 六、知识点与 OS 原理的对应

| 实验中的知识点 | 对应的 OS 原理 | 含义、关系与差异 |
|---|---|---|
| Sv39 三级页表与 `satp` | 虚拟内存与地址翻译 | **含义**：页表把虚拟页号翻译为物理页号，`satp` 保存根页表物理页号与模式。**关系**：本实验建立了最基本的映射（1 GiB 大页）。**差异**：真实系统按进程维护页表并在切换时更换 `satp`，本实验只有内核一份页表，尚无地址空间隔离 |
| 启动页表的恒等映射 | 内核空间的映射策略 | **含义**：让内核在开启分页前后都能访问同一段物理内存。**关系**：对应真实内核的"直接映射区"设计。**差异**：真实内核通常永久保留直接映射；本实验只在启动阶段需要，属于临时手段 |
| `struct Page` 描述符数组 | 页框管理（page frame） | **含义**：每页一个描述符记录引用计数与状态。**关系**：与 Linux 的 `struct page` 同构。**差异**：本实验描述符数组静态铺在内核之后，不支持内存热插拔，也没有 NUMA 等概念 |
| `PG_reserved` 保留区 | 内核保留内存 | **含义**：内核、固件、页表、描述符自身占用的页不可分配。**关系**：对应 OS 启动时"保留已用内存"的常规做法。**差异**：真实系统由引导协议（如 E820）直接给出保留区，本实验由内核自己推算 |
| First-Fit / Best-Fit 空闲链表 | 连续内存分配算法 | **含义**：用空闲块链表 + 块长记录实现连续页分配与合并。**关系**：经典 `malloc` 与早期内核分配器的同款结构。**差异**：真实内核普遍用 Buddy + Slab/SLUB 替代，以降低外部碎片并支持任意大小对象 |
| Buddy System（Challenge） | 伙伴系统 | **含义**：按 2 的幂分块，分配时分裂、释放时与伙伴合并。**关系**：Linux 物理页分配器的核心算法。**差异**：本实现省略了 zone/迁移类型、每 CPU 页缓存等工程优化 |
| `pmm_manager` 函数指针表 | 面向接口的模块化设计 | **含义**：把分配算法抽象为统一接口，调用方与实现解耦。**关系**：对应内核中的 `allocator` 抽象。**差异**：真实内核多用编译期配置或多实例并存，本实验是单实例指针 |
| DTB 物理内存探测 | 固件与内核的接口约定 | **含义**：引导程序把硬件描述交给内核。**关系**：对应 x86 的 E820/ACPI。**差异**：DTB 是 RISC-V/ARM 生态的标准，x86 不使用 |

### OS 原理中重要、但本实验未覆盖的知识点

1. **中断与异常处理**：本实验唯一接触到的异常是启动期的取指错误（通过 QEMU 日志观察，内核自身尚无 trap 处理）；中断入口、上下文保存恢复、时钟中断等属于 lab3。
2. **进程与线程**：没有 PCB、没有上下文切换，`kern_init` 是唯一的执行流；相关机制在 lab4、lab6。
3. **用户态与系统调用**：内核始终运行在 S 模式，不存在 U 模式与系统调用分发（lab5）。
4. **页表与进程地址空间**：只有一份内核页表，没有按进程隔离的地址空间、缺页处理与页面置换（lab4、lab9）。
5. **同步与并发**：单执行流，无需考虑竞态（lab7）。
6. **文件系统与设备驱动**：无（lab8）。
7. **多核支持**：`entry.S` 保存了 `hartid` 但未使用，系统按单核运行。

本次实验全程按"给出需求 → AI 生成 → 编译运行验证 → 修正"的循环推进，实际体会如下：

## 八、分支任务：双重 GDB 调试页表翻译

**负责人：贾钧涵-2412422**

### 8.1 任务与原理

手册的分支任务要求"用 gdb 调试一下正在调试 ucore 代码的 qemu 源码"。在虚拟内存模式下，CPU 执行访存指令时产生的是虚拟地址，需经 MMU 翻译：先查 TLB，未命中再依据 `satp` 指向的页表逐级查找。真实硬件上这一过程不可见，但 ucore 运行在 QEMU 模拟的 virt 平台上，"硬件行为"在 QEMU 中即为 C 代码，因而可以设断点、单步观察。

任务目标有两个：一是通过对比模拟器实现理解地址翻译的全过程；二是练习借助大模型搭建一套调试流程。

### 8.2 准备带调试信息的 QEMU

通过 apt 安装的 QEMU 8.2.2 剥离了调试符号，gdb 无法设源码断点。因此重新编译一个带调试信息的版本，且**不执行 `make install`**，使系统中同时保留"正式版"与"调试版"两个 QEMU：

```bash
sudo apt install -y build-essential ninja-build pkg-config \
    libglib2.0-dev libpixman-1-dev libslirp-dev
cd ~ && wget https://download.qemu.org/qemu-8.2.2.tar.xz && tar xvJf qemu-8.2.2.tar.xz
cd qemu-8.2.2
./configure --target-list=riscv64-softmmu --enable-debug --disable-docs
make -j$(nproc)
```

产物为 `build/qemu-system-riscv64`，`file` 显示 `with debug_info, not stripped`。调试时通过 `make debug QEMU=<调试版路径>` 覆盖 Makefile 内的 QEMU 变量，无需修改仓库文件。

### 8.3 三个终端的协作

| 终端 | 命令 | 作用 |
|---|---|---|
| 1 | `make debug QEMU=~/qemu-8.2.2/build/qemu-system-riscv64` | 启动 QEMU，`-s -S` 使其停在复位状态 |
| 2 | `sudo gdb -q -nx <调试版> -p <QEMU_PID>` | 附加到 QEMU 进程，调试其源码 |
| 3 | `riscv64-unknown-elf-gdb bin/kernel` | 通过 QEMU 的 gdbstub 控制内核执行 |

终端 2 需要 root 权限：Ubuntu 默认 `kernel.yama.ptrace_scope = 1`，普通用户只能调试自己的子进程，附加到 QEMU 会被拒绝并报 `ptrace: Operation not permitted`。

终端 2 执行的 gdb 脚本：

```gdb
set pagination off
set confirm off
handle SIGPIPE nostop noprint
break get_physical_address if !is_debug && addr == 0xffffffffc02000d6
continue
```

- `handle SIGPIPE nostop noprint`：避免 QEMU 写管道产生的信号打断调试；
- 条件 `!is_debug`：过滤 gdb 自身读内存触发的地址翻译；
- 条件 `addr == 0xffffffffc02000d6`：把观察点限定为内核跳转到 C 入口的那一次。

终端 3 执行的 gdb 脚本：

```gdb
set remotetimeout unlimited
target remote :1234
break *0x80200000
continue
```

`set remotetimeout unlimited` 是必需的：终端 2 停住 QEMU 时，终端 3 的请求长时间得不到响应，默认超时会报 `Ignoring packet error, continuing...`。

### 8.4 调试结果

命中时的输出（地址已换算为十六进制）：

```
Thread 2 "qemu-system-ris" hit Breakpoint 1, get_physical_address
    (env=..., physical=..., ret_prot=..., addr=18446744072637907158,
     fault_pte_addr=0x0, access_type=2, mmu_idx=1,
     first_stage=true, two_stage=false, is_debug=false)
    at ../target/riscv/cpu_helper.c:801
(gdb) p/x addr
$1 = 0xffffffffc02000d6
```

`0xffffffffc02000d6` 正是 `kern_init` 的虚拟地址，且 `access_type` 为取指，对应内核从入口 `jr` 到 C 代码入口时的第一次取指。

调用栈（自内向外）：

```
#0  get_physical_address       ← Sv39 三级页表遍历
#1  riscv_cpu_tlb_fill         ← TLB 未命中后的填充处理
#2  probe_access_internal
#3  get_page_addr_code_hostp
#4  get_page_addr_code
#5  tb_htable_lookup
#6  tb_lookup
#7  helper_lookup_tb_ptr       ← 查询翻译块缓存
#8  code_gen_buffer
#9  cpu_tb_exec ...            ← TCG 执行循环
```

用 gdb 便利变量保存出参后再 `finish`，可读取翻译结果：

```gdb
set $p = physical
finish
p/x *$p
```

```
Return value is $2 = 0
$3 = 0x802000d6
```

即虚拟地址 `0xffffffffc02000d6` 被翻译为物理地址 `0x802000d6`，与 `va_pa_offset = 0xFFFFFFFF40000000` 的换算关系一致。

### 8.5 调用路径的含义

| 层次 | 函数 | 含义 |
|---|---|---|
| TCG 执行 | `cpu_tb_exec`、`code_gen_buffer` | 执行已翻译好的宿主机代码块 |
| 翻译块缓存 | `helper_lookup_tb_ptr`、`tb_lookup`、`tb_htable_lookup` | 按 PC 查找缓存的翻译块，本例未命中 |
| 取指地址解析 | `get_page_addr_code`、`probe_access_internal` | 确定该虚拟代码在宿主机内存中的位置 |
| TLB | `riscv_cpu_tlb_fill` | RISC-V TLB 未命中的处理入口 |
| 页表遍历 | `get_physical_address` | 依 `satp` 逐级读取三级页表，得到物理页号 |

这一路径说明了"硬件完成"与"软件模拟"的对应关系：真实 CPU 由 MMU 硬件并行完成 TLB 查询与页表遍历；QEMU 用上述 C 函数串行实现同样语义，因此可被断点与单步观察。

### 8.6 遇到的问题与解决

| 现象 | 原因 | 解决 |
|---|---|---|
| `ptrace: Operation not permitted` | Yama 限制，禁止附加非子进程 | 按手册改用 `sudo gdb` |
| `bt` 中出现 `wait4`、`reap_children` | `pgrep -f` 同时匹配到 `make`（其命令行含 QEMU 路径） | 用 `pgrep -af` 人工辨认，或用 `^/path/to/qemu` 锚定 |
| 首次命中时 `is_debug=true`、`addr=4096` | gdb 自身读内存也会触发地址翻译 | 断点条件加 `!is_debug` |
| `Ignoring packet error` | 终端 2 停住 QEMU 后终端 3 请求超时 | `set remotetimeout unlimited` |
| 多行命令粘贴被合并为一行 | gdb 行编辑器的粘贴行为 | 写入 `/tmp/*.gdb` 后用 `-x` 执行 |
| `No symbol "physical" in current context` | `finish` 后原栈帧的局部变量已销毁 | 先用 `set $p = physical` 保存指针 |

### 8.7 小结

分支任务验证了：ucore 运行在 QEMU 模拟的 virt 平台上，地址翻译这一"硬件行为"在模拟器中由 `get_physical_address` 等软件函数实现；借助双重 GDB，可以同时观察内核侧的访存指令与模拟器侧的翻译过程。相比直接阅读源码，这种方式更直观地建立了"虚拟地址 → 页表 → 物理地址"的印象。

手册提示的"条件断点"思路在实践中同样有效：`get_physical_address` 每次翻译都会被调用，若不限定地址，调试过程只能反复 `continue`；把条件设为某个必然被访问的地址（例如内核 C 入口），即可精确停在目标时刻，甚至无需调试内核侧。
